# SOULFORGE — MASTER DEVELOPMENT PROMPT FOR CODEX

## ROLE AND OBJECTIVE

You are the lead software engineer, game systems architect, technical game designer, and implementation agent for a new browser-based 3D fantasy RPG called **Soulforge**.

Your responsibility is to design, implement, test, document, and prepare Soulforge for deployment as a complete, playable web game.

This is an actual game development project, not a static website, mockup, documentation-only exercise, or proof of concept.

**Primary objective:** Build a functional, polished, classless, third-person fantasy RPG featuring character progression, equipment, exploration, real-time combat, quests, loot, and a unique custom spell creation system.

Players must be able to create an account, create a character, enter a 3D fantasy world, fight enemies, earn experience, collect and equip items, assign attribute points, invent their own spells, complete quests, save their progress, and continue playing in future sessions.

The initial release will be a single-player experience using Firebase for user authentication, character persistence, and web hosting.

Design the architecture so multiplayer features can be added in the future without requiring a complete rewrite, but do not implement multiplayer networking in the initial release.

# 3. CORE GAME DESIGN PHILOSOPHY

Soulforge is completely classless.

Players do not select Warrior, Mage, Rogue, Paladin, or any other predefined class.

Instead, character identity emerges from three interconnected systems:

**Attributes determine character strengths.**

**Equipment determines available combat capabilities and provides specialized bonuses.**

**Custom spellcrafting determines magical abilities.**

A character should be capable of combining traditional RPG archetypes.

Examples include:

- Heavy-armored fire battlemage
- Dual-dagger poison specialist
- Bow-wielding arcane ranger
- Defensive shield mage
- Two-handed warrior with healing magic
- Lightning-focused melee fighter
- Spellcaster wearing medium armor
- Self-healing frontline fighter

These are potential player-created builds, not selectable classes.

Build experimentation is a central part of the game.

# 4. HYBRID ATTRIBUTE REQUIREMENT SYSTEM

Soulforge uses a hybrid system.

Basic weapons, armor, and introductory magic are accessible to all characters.

Advanced equipment and spell components require specific attribute investments.

Players should never be completely prevented from using basic magic or physical combat simply because they favor another style.

### Primary Attributes

Implement six primary attributes.

**Strength**
- Increases physical melee damage
- Supports heavy weapons
- Unlocks advanced strength-based equipment

**Dexterity**
- Influences attack speed
- Improves ranged weapon effectiveness
- Contributes to critical strike chance
- Supports agile equipment

**Intelligence**
- Increases magical damage
- Contributes to available spell complexity
- Unlocks advanced magical components

**Vitality**
- Increases maximum health
- Improves health regeneration

**Endurance**
- Increases maximum stamina
- Improves physical defense
- Supports heavy armor effectiveness

**Willpower**
- Increases maximum mana
- Improves mana regeneration
- Contributes to magical stability or control

### Starting Attributes

For the initial implementation:

- Every character begins with 5 points in each attribute.
- Characters receive 5 additional points to allocate during creation.
- Each level awards 3 attribute points.

Keep these values configurable in one centralized balance configuration.

### Derived Statistics

Calculate derived stats from attributes and equipment.

At minimum:

- Maximum health
- Maximum mana
- Maximum stamina
- Physical damage
- Magical damage
- Physical defense
- Magic resistance
- Critical chance
- Attack speed
- Movement speed
- Spell complexity capacity
- Mana regeneration
- Health regeneration

Use deterministic formulas with documented values.

Prevent invalid states such as negative health, non-finite damage, and attribute totals exceeding earned points.

### Level Progression

Initial maximum level: 10.

Experience is earned through:

- Defeating enemies
- Completing quests
- Defeating bosses
- Discovering designated exploration locations

Create an experience progression curve with increasing requirements.

All level thresholds must be configurable.

Provide an initial attribute respec system so players can experiment with different builds.

Respeccing must unequip incompatible advanced equipment and disable or unequip spells that no longer meet requirements, without deleting owned items or spell designs.

# 9. SPELLFORGE — CUSTOM SPELL CREATION

This is Soulforge's signature feature and one of the highest priorities.

Players do not simply learn fixed spells from a conventional skill tree.

Instead, they create spells by combining unlocked magical components.

The Spellforge must exist as a functional React interface and a corresponding gameplay system.

### Spell Components

A spell is assembled from three main component categories.

## A. Element

Initial elements:

**Fire**
- Direct magical damage
- Optional burning effects

**Frost**
- Magical damage
- Optional slowing effects

**Arcane**
- Pure magical damage
- Magical shielding or utility

**Nature**
- Damage or healing depending on spell form
- Regeneration and defensive possibilities

## B. Spell Form

Initial forms:

**Projectile**
- Casts magic toward a target
- Supports single-target damage or healing when valid

**Nova**
- Releases magic around the caster
- Supports area effects

**Weapon Enchantment**
- Temporarily applies magic to an equipped weapon
- Supports magical damage bonuses or special on-hit effects

**Barrier**
- Creates a protective magical effect
- Supports shields and temporary defensive bonuses

## C. Modifier

Initial modifiers:

**None**
- No additional modifier

**Chain**
- Allows eligible effects to jump between targets

**Lingering**
- Adds duration or damage-over-time behavior

**Empowered**
- Increases effect power at an additional resource cost

### Spell Creation Workflow

The player opens the Spellforge menu.

The interface must allow players to:

1. Select an unlocked element.
2. Select a compatible spell form.
3. Select a compatible modifier.
4. Preview the generated spell.
5. View required attributes.
6. View complexity cost.
7. View mana cost.
8. View cooldown.
9. View estimated damage or other effects.
10. Name the spell.
11. Save the spell.
12. Assign it to an action bar slot.

The system must create actual usable gameplay abilities.

### Spell Data Structure

Design a typed serializable structure conceptually similar to:

```typescript
interface CreatedSpell {
  id: string;
  name: string;
  elementId: string;
  formId: string;
  modifierId: string | null;
  complexityCost: number;
  manaCost: number;
  cooldownSeconds: number;
  requirements: Partial<CharacterAttributes>;
  version: number;
}
```

Extend the model as required for game mechanics.

Do not store executable functions or arbitrary player-generated code in spell records.

Spell execution must use trusted, predefined component behavior.

### Spell Complexity

Every spell component has a complexity cost.

Calculate total complexity using its elements, form, and modifier.

A character can only equip spells that fit within their current spell complexity capacity.

Intelligence should increase complexity capacity.

Advanced components may also require minimum Intelligence or Willpower.

Keep spell eligibility and component compatibility as separate validation rules.

### Spell Validation

Not every combination should automatically be valid.

Examples:

- Chain may only work on suitable targeting forms.
- Lingering may modify eligible damage, regeneration, or defensive effects.
- Weapon enchantments require compatible equipment.
- Healing effects must correctly distinguish allies, self, and enemies.
- Barrier effects must grant defensive benefits instead of incorrectly producing damage.

Implement a compatibility system and provide clear feedback when a combination is invalid.

### Spell Balance

Mana cost, damage, healing, duration, and cooldown must be calculated from configurable component values.

Avoid arbitrary hardcoded values scattered throughout UI components.

Spell designs must be revalidated on load and execution.

Players must not be able to edit Firestore documents to create spells with impossible damage, zero cooldowns, or unauthorized components.

### Spell Visual Effects

Use distinct particle effects and visual colors for each element.

The spell form should determine how the effect appears in the 3D world.

Examples:

- Projectile: traveling magical effect
- Nova: expanding radial effect
- Weapon enchantment: glow or particle effects attached to a weapon
- Barrier: visible magical shield around the character

Use reusable effect systems rather than hardcoding separate implementations for every spell combination.

### Saved Spells

Players must be able to:

- Save custom spells
- Rename spells
- Delete spells
- Edit an existing spell
- Equip spells
- Unequip spells
- Assign spells to action bar slots

Initially support up to six equipped spells.

Store created spell configurations in Firebase.

# 15. FIREBASE ARCHITECTURE

Firebase will be responsible for:

- Account authentication
- Character persistence
- Inventory persistence
- Equipment persistence
- Attributes and progression
- Saved custom spells
- Quest progress
- Player settings
- Web hosting

### Authentication

Implement:

- Email/password registration
- Email/password login
- Password reset
- Logout
- Persistent authenticated sessions
- Account deletion

Optionally support Google sign-in if it can be added without delaying the initial implementation.

### Suggested Firestore Data Layout

Use a structure similar to:

```text
users/{uid}
    profile
    settings

users/{uid}/characters/{characterId}
    name
    level
    experience
    attributes
    currentHealth
    currentMana
    currentStamina
    gold
    location
    progressionVersion

users/{uid}/characters/{characterId}/inventory/{itemInstanceId}

users/{uid}/characters/{characterId}/equipment/{slotId}

users/{uid}/characters/{characterId}/spells/{spellId}

users/{uid}/characters/{characterId}/quests/{questId}

users/{uid}/characters/{characterId}/unlocks/{unlockId}
```

Adjust this layout when justified by read patterns, security, document size, and atomic update requirements.

### Static Game Data

Store static item definitions, enemy definitions, quest definitions, spell components, and balance configurations in version-controlled TypeScript or JSON files.

Do not duplicate large static game catalogs in every player's Firestore documents.

### Persistence Rules

Character progress should save at meaningful milestones:

- Quest completion
- Leveling up
- Attribute changes
- Equipment changes
- Inventory transactions
- Spell creation
- Spell changes
- Player logout
- Periodic safe checkpoints

Avoid writing to Firestore every frame or for every movement update.

Use debounced or event-driven saving where appropriate.

### Security

Implement Firebase Security Rules.

Players must not be able to access another player's private character data.

Validate document ownership, field types, schema constraints, and allowed operations.

Do not assume user ownership alone prevents cheating.

Firestore Security Rules cannot reliably validate an entire complex RPG economy or arbitrary combat results on their own.

For an initial single-player version, locally calculated combat, experience, gold, and loot may be saved as player-owned progress and should explicitly be considered **client-trusted and potentially modifiable**.

Do not claim this model is cheat-proof.

If competitive rankings, trading, shared economies, or multiplayer are introduced, move reward granting, inventory mutations, combat validation, and other sensitive operations to authoritative backend services.

Use Firebase App Check where practical as an additional abuse-reduction measure, not a replacement for authorization.

### Firebase Configuration

Use environment variables for client Firebase configuration.

Include:

```text
VITE_FIREBASE_API_KEY
VITE_FIREBASE_AUTH_DOMAIN
VITE_FIREBASE_PROJECT_ID
VITE_FIREBASE_STORAGE_BUCKET
VITE_FIREBASE_MESSAGING_SENDER_ID
VITE_FIREBASE_APP_ID
```

Do not include private service account credentials in frontend code.

Firebase client configuration is not a secret and must not be treated as an authorization mechanism.

Provide `.env.example` and appropriate Git ignore rules.

Do not invent production credentials or silently deploy to an unknown Firebase project.

# 24. PROJECT EXECUTION RULES

Follow these instructions during development.

1. Inspect the existing repository before modifying files.

2. If the repository is empty, initialize the application using the chosen stack.

3. Create a practical implementation plan and maintain progress in a `PROJECT_PLAN.md` file.

4. Build the application incrementally, but actually write and integrate the code.

5. Do not stop after generating a project plan or directory structure.

6. Implement complete vertical slices rather than scattering incomplete features throughout the project.

7. Prefer working gameplay over complicated abstractions.

8. Make reasonable implementation decisions without repeatedly asking for approval.

9. Ask for user input only when genuinely necessary, such as missing Firebase credentials, a required project selection, or access to external services.

10. Do not invent credentials, external assets, or completed test results.

11. Keep the application runnable after each milestone.

12. Use original, maintainable code.

13. Avoid paid libraries, proprietary game engines, and licensed commercial assets that would create unnecessary distribution restrictions.

14. Document any third-party asset licenses and attribution requirements.

15. Never expose Firebase administrative credentials.

16. Never silently weaken security rules to work around permission errors.

17. If a feature is too large for the current implementation phase, provide the smallest complete functional version and record future improvements.

18. Do not replace gameplay with screenshots, mockups, or static menus.

19. Track completed functionality separately from planned functionality.

20. Prioritize the core Soulforge experience: movement, combat, character builds, loot, and custom spell creation.

# 25. MVP DEFINITION OF DONE

The initial release is complete when a new user can:

1. Open Soulforge in a desktop browser.
2. Register an account.
3. Create a character.
4. Enter a stylized 3D fantasy world.
5. Move freely using third-person controls.
6. Interact with NPCs.
7. Accept quests.
8. Target and fight enemies.
9. Gain experience and level up.
10. Allocate attribute points.
11. Obtain equipment and gold.
12. Equip items according to attribute requirements.
13. Open the Spellforge.
14. Combine magical elements, spell forms, and modifiers.
15. Create, name, and save a custom spell.
16. Equip the created spell.
17. Cast the spell during real-time combat.
18. Defeat the starter-zone boss.
19. Receive quest and loot rewards.
20. Log out and later reload saved progress.

All major actions must work in the actual game.

The game must include appropriate testing and error handling.

The first release does not need to be an MMO, feature dozens of regions, or contain hundreds of items.

It must provide a cohesive, enjoyable, replayable foundation for a larger fantasy RPG.
